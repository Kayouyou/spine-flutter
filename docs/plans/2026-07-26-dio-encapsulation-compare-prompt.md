# 增强提示词：Dio 封装对比分析 + 改造建议

> 用途：让 AI 拉取外部 Gitee 仓库的 Dio 封装实现，与当前 spine_flutter 项目的 Dio 封装做基于真实代码的逐维度对比，产出「对比报告 + 优先级改造清单」。

---

## 提示词正文（可直接复制使用）

```text
你是一名资深 Flutter 架构师，精通 Dio 网络层封装与 Clean Architecture。
你的任务：拉取并阅读外部 Gitee 仓库中 Dio 网络请求库的封装实现，与「当前项目」（spine_flutter 公共骨架，Dio 封装位于 packages/infrastructure/lib/api/）的同类实现，做基于真实代码的逐维度对比，并产出对比分析报告 + 一份按优先级排序的改造建议。

========== 第一步：获取并阅读真实代码（禁止凭印象） ==========
1. 克隆参考仓库：
   git clone https://gitee.com/_preject/flutter_start.git /tmp/flutter_start_ref
2. 在克隆产物中定位 Dio 封装相关代码（典型路径：network/、api/、http/、core/ 下的 client / interceptor / token / error 相关文件），列出关键文件路径。
3. 阅读当前项目 packages/infrastructure/lib/api/ 下的对应实现，列出关键文件路径。
4. 对比必须引用「具体文件路径 + 类名/函数名 + 关键代码片段」，不得泛泛而谈。

========== 第二步：逐维度对比（维度已去重，互不重叠） ==========
对每个维度分别说明：Gitee 仓库的做法 / 当前项目的做法 / 差异点。

A. 统一拦截体系
   - 请求拦截器（统一加 Header、BaseUrl、日志、鉴权注入）
   - 响应拦截器（统一解析、状态码 / 业务码处理）
   - 异常统一出口（是否集中捕获并转成统一错误模型）
B. 错误处理与异常捕获机制
   - 错误类型划分（网络错误 / 超时 / 业务错误 / 解析错误）
   - 异常捕获位置与统一处理链路
   - 是否提供可观测的错误上报钩子（对接 ErrorReporter 之类）
C. 超时、取消与请求管理
   - 连接 / 接收超时配置方式
   - 请求取消机制（CancelToken 使用）
   - 动态销毁、请求入队、避免内存泄漏
D. 弱网优化（动态超时 / 智能重试 / 熔断保护）
   - 是否支持按网络状况动态调超时
   - 失败重试策略（指数退避、重试次数、可重试判定）
   - 熔断 / 降级保护机制
E. 鉴权与 Token 机制
   - Token 注入方式
   - Token 过期自动刷新（刷新接口、并发请求排队、刷新失败处理）
   - 是否做到刷新期间不中断用户操作流程
F. 统一响应数据模型封装
   - 响应泛型 / Result 模型设计
   - 状态码、业务错误码、分页模型封装
   - 与 Domain 层实体（如 Result<T,E>）的衔接
G. 架构清晰度
   - 分层与职责边界（是否便于替换实现 / 单测）
   - 可维护性、可扩展性、与现有 DI（get_it + injectable）的契合度

========== 第三步：产出交付物（Markdown） ==========
1. 概览：两边封装各一句话定位 + 整体观感。
2. 维度对比表：维度 | Gitee 仓库 | 当前项目 | 差异。
3. 逐项差异详述：对应第二步 A–G，引用真实代码。
4. 借鉴点与优势点：
   - 明确列出 Gitee 仓库中值得当前项目借鉴的设计 / 模式 / 特性，逐条写清「借鉴什么 + 理由 + 当前项目落地成本（低 / 中 / 高）」。
   - 客观说明当前项目已更优的方面（避免盲从），写清「优在哪里」。
5. 优先级改造清单：把可落地项拆成 P0（高价值低风险，建议立即做）/ P1 / P2，每条含「改什么 + 改到哪个文件 / 模块 + 预期收益」。

========== 约束 ==========
- 全程中文。
- 所有结论必须基于实际读到的代码并标注来源路径；若某仓库未实现某维度，明确写「未实现」而非猜测。
- 不盲目推崇外部仓库；当前项目更优处要同等呈现。
```

## 相对原草稿的改动说明

1. **去重合并**：原「5 个对比点 + 5 个能力项」存在大量重叠（统一拦截≈请求/响应拦截器；请求管理≈请求取消与超时；Token 过期刷新≈Token/鉴权自动刷新）。已整合为 7 个互不重叠的维度 A–G。
2. **新增独立维度「弱网优化」**：原草稿只在能力项里提了「动态超时/智能重试/熔断保护」，未进入正式对比维度；现提升为维度 D，单列对比。
3. **强制真实代码**：原草稿没说怎么拿到 Gitee 代码。已加入「第一步：克隆 + 定位 + 引用文件路径/类名/片段」硬约束，避免 AI 凭印象空谈。
4. **锚定当前项目身份**：明确「当前项目 = spine_flutter 公共骨架，Dio 封装在 packages/infrastructure/lib/api/」，与原草稿的模糊「当前项目」区分开。
5. **明确交付物形态**：按你的选择定为「对比报告 + 优先级改造清单」，并规定产出包含概览、对比表、差异详述、借鉴/优势点、P0/P1/P2 改造清单五部分。
6. **增加落地成本与可行性评估**：借鉴点要求附「落地成本（低/中/高）」，改造清单要求到「文件/模块 + 预期收益」，让结论可直接行动。
7. **防盲从约束**：要求客观呈现当前项目更优处，未实现的维度写「未实现」而非猜测。
